# 2026-08-17 Orchestrator Archive Queue Resume

## 变更背景 / 目标

同一项目的归档任务需要保持容量一和 FIFO 串行：后续任务在持锁任务结束前等待，正常释放后继续；不同项目之间仍可并行。实现还必须在 Windows 与 Linux 上避免活锁被 stale 阈值误回收，并在归档多文件状态写入中断后安全恢复。

## 具体变更内容

- 保留项目级 capacity-one merge pool，不增加机器级 archive lock，也不消耗 Tester host permit。
- 持久化 archive candidate，并在 enqueue、acquire 和中断恢复时重新校验 worktree change ID 与 base heads；漂移返回 `EXECUTING`。
- 正常 archive release 与 project status 暴露同项目 `next_ready` Worker 回调，丢失 wakeup 后仍可重试。
- 内部目录锁增加 owner token、PID 和 heartbeat；只有确认 owner 进程退出后才回收 stale lock。Windows 使用只读进程句柄查询，Linux 使用 POSIX signal 0，不使用平台专用文件锁。
- archive revalidation/acquisition 在 Task、lease、ticket 多文件变更前写入 project-local operation record；后续 mutation 先 reconcile，避免永久队头或不一致 lease。
- `BLOCKED -> WAITING_FOR_MERGE` 保留先前已验证 candidate，禁止把恢复期间的未测试漂移重标为 justified skip。
- merge stale inspection 能发现 legacy archive host-only orphan；显式 reclaim 后保持 Task queued。等待态的 stale partial project lease 作为 audited orphan admission 回收，不创建无关 recovery hold。
- skill 同步递归排除 `__pycache__`、`.pyc`、`.pyo`，并修正 workflow 步骤编号。

## 经验 / 教训摘要

- 目录 mtime 超时不能证明锁 owner 已退出；活性与过期必须分开判断。
- Task、lease、ticket 的原子文件写入并不等于跨文件事务；必须先记录 intent，再让下一次公开 mutation 收敛。
- 恢复流程不能重新捕获“当前状态”作为已验证候选，否则会绕过 test evidence。
- 兼容记录必须从目标 pool 的诊断入口可发现；仅跟随当前 project lease 引用会隐藏真正的 host-only orphan。

## 可复用排查线索

- 症状：同一 Task 出现两个 ticket；触发：candidate scan 超过 lock stale threshold；关键词：`owner.json`, `LOCK_STALE_SECONDS`, `Timed out waiting for runtime lock`；快速检查：确认 lock heartbeat 与 recorded PID 是否仍存活。
- 症状：队头 Task 已是 `EXECUTING` 但 ticket 仍在；触发：revalidation transition 后进程中断；关键词：`archive-revalidation`, `operations`; 快速检查：查看 merge pool `operations` 并触发一次安全 mutation 进行 reconcile。
- 症状：waiting Task 有 project lease 却没有 `active_lease`；触发：lease write 后进程中断；关键词：`archive-acquire`, `orphan_admission`; 快速检查：比较 Task state、operation、lease 与 ticket owner。
- 症状：Tester host capacity 被旧 archive owner 占用但 merge stale 为空；关键词：`legacy-host-orphan`, `reclaim-host`; 快速检查：用 merge pool stale inspection 查 Task 的 legacy/v2 owner。

## 关键设计决策与权衡

- 采用项目级 FIFO/lease 而不是全局 archive lock，以保留不同项目并行能力。
- acquisition 保持非阻塞；`next_ready` 是 retry hint，不是所有权。
- 不使用 `flock`、`msvcrt.locking` 或 named mutex；目录锁仍跨平台，但 stale reclaim 必须结合 heartbeat 与安全进程活性查询。
- archive operation journal 只覆盖直接相关的多文件状态边界，不引入数据库或第三方事务依赖。
- stale active archive 继续使用显式 recovery hold；尚未进入 active Task 的 partial lease 可审计回收并保持 queued，避免永久阻塞。

## 潜在影响

- 新 runtime lock metadata 为 additive；旧的无 owner lock 仍可按 stale 路径恢复。
- PID 被系统复用时 recovery 会保守等待/超时，而不会冒险偷取可能仍活跃的 lock。
- project-local operation record 在 reconcile 完成前会让 `next_ready` 返回空，避免错误 wakeup。
- 真实 Linux 主机尚未执行本次测试；实现与测试无 Windows-only file-lock dependency，但 Linux execution 仍是残余验证风险。
