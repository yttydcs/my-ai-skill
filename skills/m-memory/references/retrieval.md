# Retrieval and source-bound representations

## Task-directed lexical retrieval

Choose scope from the task and the project's actual metadata, not from a universal project model. For governed docs, behavior normally starts in `features`, intent/acceptance in `requirements`, technical contracts in `specs`, architectural rationale in `decisions`, and symptoms in `lessons`. Enter `intake`/`change` when origin, an earlier decision or a completed rollout matters. Select the most relevant category first rather than issuing every category query. Use a project's broader stable-document group only if that metadata is explicitly defined. Category membership alone does not prove currency; `lifecycle=current` is useful only when that convention is actually populated. Never add an invented filter and treat the empty result as absence.

Lexical queries should carry a few discriminating concepts rather than the whole conversational request. Preserve API names, error codes, product names, numbers and relevant negation/conditions. When the request and corpus use different languages, reformulate with equivalent technical terms in the corpus language or a compact bilingual query. Do not invent an identifier, add a guessed answer, translate an opaque ID, or upload project text to an unselected translation/embedding service. The local Agent can formulate these queries itself.

Use BM25 for a small set of domain terms; use FTS deliberately when known terms, headings or error identifiers give a more selective query. FTS is token-based, not an exact substring guarantee, and the server's `simple` configuration does not segment a full Chinese sentence. `search --method bm25|fts --limit 3` selects a per-call method and small candidate set without rewriting the binding. Other configured methods remain explicit choices, with their required vectors supplied by the caller. Do not silently switch methods after a transport, authorization, revision or coverage error.

Normally issue one targeted discovery query, inspect it, and stop when the required evidence is sufficient. If the response succeeded but does not provide the needed evidence, identify the gap: wording/language, unsuitable category, wrong document, or missing passage. Then deliberately change only the relevant part—reformulate, select another permitted category/method, or search/read within the observed object revisions. A plausible document with a poor first snippet is a reason to read its relevant section, not repeatedly search the whole library. Do not automatically run the original question, a translation, every method and every category together.

Keep one retrieval/context budget for the task, including follow-up calls and result metadata; a per-response byte cap is not a total-task cap. Start with a few candidates (usually three) and expand only for a concrete unresolved evidence need. Do not repeat already sufficient, unchanged evidence or accumulate broad history. An unsuccessful bounded search leaves a fact unverified; it does not prove that the fact is absent. Keep query choices and transient traces local, with no knowledge writes merely for retrieval.

Before implementing a contract or giving a definitive rule, check coverage of the task's conditions and exceptions within the selected current source, including later amendments or superseding sections. `status=current` means the object revision is current; its opening paragraph can still be qualified later in the same object. For a short relevant contract, a bounded whole-object read may be cheaper and more complete than several discovery queries. Otherwise read its relevant section sequence or explicitly search that observed object revision for the unresolved condition/update, after confirming capability support. A keyword miss alone does not prove there is no amendment. Do not preload unrelated documents or history; if this check cannot fit the remaining budget, describe the conclusion as partial. Reserve follow-up budget for unresolved source conditions rather than spending it all on new candidates; a multi-part task needs coverage of each requested part, not just more queries for one plausible topic.

## Evidence and source reads

Use a current summary when it contains the facts needed for the task. If a required number, date, condition, exception or specific cause is missing, fetch the relevant source span within the selected libraries and remaining budget. A broad summary or an object's name does not establish the missing detail. If the source cannot be read within those constraints, state which fact remains unverified; do not silently increase the budget or scope. This does not require fetching every summary's full source or loading its history.

When citing retrieved knowledge, preserve the exact library, object and revision combination actually read. A summary's identity and revision belong to that summary; a dependency pointing to a source is a navigation anchor, not proof that its text was read. Cite the summary for claims it supports, or read and cite the source with its own revision. Treat IDs and any client-provided aliases as opaque; do not shorten a summary ID into a source ID while retaining the summary revision.

Check that each cited passage supports the particular claim. A valid ID for a different entity or an unrelated search hit is not supporting evidence. Keep this check local to the answer or change being justified; it does not authorize a provenance crawl, a stored query trace or a new knowledge write.

Use `memory_client.py --binding <path> capabilities` for `/v1/capabilities`, and `check` for the selected library's `/section-indexes`. The capability command reads only the fixed bound-origin endpoint with the same TLS, credential, redirect and response-budget protections; it does not list libraries or grant access to any new library. Read capabilities when needed and reuse them within the task. A section index is a rebuildable representation of current text, not a summary or a second authoritative document. Queries use the chosen index ID and `expected_index_revision`. Model ID, preprocessing ID and dimension must match for semantic queries; the server never calls a model itself.

Use the question and configured semantic encoder for paraphrase retrieval, or explicit keywords for lexical retrieval. Available section methods are `fts`, `vector_exact` and `hybrid` (FTS plus exact cosine, RRF with constant 60). These are choices, not a universal best strategy. PostgreSQL `simple` FTS does not segment Chinese sentences into words. The exact vector path scans eligible embeddings; measure latency before selecting it for a large library.

`POST /v1/libraries/{library}/section-indexes/{index}/search` takes `target`, `limit`, `per_object_limit`, `budget_bytes`, `allowed_source_libraries` and an explicit method. Vector requests also take `model_id`, `preprocessing_id` and `query_vector`; hybrid adds a lexical `query`. `complete_index` fails if eligible visible objects lack vectors; `current_hits` allows partial coverage and reports missing coverage. Neither permits stale revision hits. The overall byte budget includes result metadata; `truncated` means there may be more evidence, not that there were no relevant results.

Returned spans contain exact source text, object/revision identity, character offsets and line numbers. Read additional sections with `GET .../{index}/objects/{object}?expected_revision=...&offset=...&limit=...&budget_bytes=...`; advance offset by the number of returned sections. If a budget admits no section, explicitly increase it rather than looping at the same offset. Retrieve only the needed current sections; load provenance/history separately when asked.

For a second search inside selected documents, check that the relevant `section_search` or `document_search` capability advertises `object_revisions`. Pass a mapping of 1–50 same-library object IDs to the revisions returned by discovery. It intersects the chosen target and metadata filter; all five section/document methods honor it, including their vector coverage checks. The response must echo the normalized mapping exactly, and every result must match a selected ID/revision. Missing capability or echo means unsupported semantics, not an empty result or permission to broaden the search. Old services may ignore unknown input fields. A selected current revision changing returns 409; missing/deleted/cross-library or inaccessible objects return 404. Restricted summary sources remain hidden, and stale summaries return 409. An empty mapping is invalid. BM25 corpus statistics use the selected eligible objects, so scores from this step are not directly comparable to scores from a larger discovery corpus. The echoed mapping consumes response budget too.

Use this option when discovery found plausible documents but their first snippets do not answer the question. Choose the next keywords, encoder, documents and follow-up reads explicitly. Stop at the task's request/context budget; no match is not evidence that an unsearched document lacks the answer. Keep the query/read trace local unless it produces a separately justified durable knowledge change. Selecting documents never authorizes importing them into a local mirror, rewriting their metadata for filtering, or starting an automatic query/model loop on the server.

Embedding production is an explicit maintenance operation. Read current sections, encode their text with the configured model, and `PUT .../{index}/objects/{object}/embeddings` with `expected_index_revision`, `expected_object_revision`, optional `allowed_source_libraries`, and items containing `section_id`, `expected_embedding_revision` (null for a missing vector) and `embedding`. The batch is atomic. A 409 requires rereading the affected versions; never relabel a vector computed from old text as current. Rebuilding an index removes its previous section vectors. Attachment changes also change the owning object's revision and invalidate old representations.

Formal summaries are `derived` objects created or edited by the local agent with explicit source dependencies. They are durable knowledge, subject to source and summary CAS checks, and survive index rebuilds. Publish them only at the workflow's durable-information boundary, not on each retrieval or tool call.

Use `dependencies` only for content actually used by a derived object. For navigation such as “this requirement came from this discussion,” any source or derived object can explicitly hold `references` in a normal commit: each item has caller-defined `relation_type` (an ASCII identifier up to 64 characters), `target_library_id`, `target_object_id`, `target_revision`, and optional `span`. The list replaces the previous list under the object's expected revision; omitting it preserves references, and `[]` removes them. A changed reference is durable metadata and changes the object's revision; merely changing a target does not invalidate its referrer. Do not create a reference for every fix or intermediate tool call.

Read references only when provenance is needed: `GET /v1/libraries/{library}/objects/{object}/references` accepts `direction=outgoing|incoming`, optional repeated `relation_types`, explicit repeated `libraries` (default only the root library), `depth`, `limit`, and `budget_bytes`. Results contain anchored revisions and relation metadata, never target bodies. `changed` means the anchor differs from current; `unavailable` means the selected target is gone. Neither proves an older body remains retained. Outgoing traversal follows only matching current anchors; an explicit `revision` can retrieve the root's retained historical references. Incoming traversal inspects current owners only, optionally filtering the target revision; it is not a historical graph reconstruction. Use the returned IDs and separate bounded object/history reads to inspect evidence. Unselected or unauthorized targets are not expanded. Respect `truncated` and the returned depth limit rather than treating a bounded response as the complete graph.

For an index deliberately configured with `lexical_profile: "unicode-word-han2-stop-v1"`, `POST .../{index}/document-search` supports `bm25` and `bm25_vector`. Both require `query`, `expected_index_revision`, explicit target/scope and a byte budget, and return one section per object (`per_object_limit: 1`). The combination also requires the compatible model/preprocessing/query vector. It fuses document ranks using RRF60; it is different from section `hybrid`. The lexical profile matches any of at most 64 distinct normalized terms, uses visible current documents for corpus statistics, and includes Han bigrams for Chinese. No corpus-wide query, implicit profile creation, or producer call is authorized by selecting a search method. A match remains a candidate for reading, not verified answer evidence.
