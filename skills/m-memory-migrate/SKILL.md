# m:memory-migrate

Use [m-memory](../m-memory/SKILL.md) for the selected service binding and its API contracts. The user selects the source docs root, destination library and migration scope; reuse choices already made in the conversation. A request to create this skill or preview files is not an instruction to migrate an existing project.

## Workflow

1. Resolve the exact source directory and target binding. If the target is not yet selected or created, use `scan` for a source-only inventory without credentials or network access; it does not require creating a library just to preview files. The eventual write library must also be readable for verification. Do not silently use the pilot library for a real project. If no target exists, prepare a concrete library/index/device setup using the service's owner interface and the user's selected policies; do not put owner credentials in project bindings.
2. Run `scripts/migrate.py preview` using [the helper contract](references/migration.md). It creates a local inventory of paths, hashes and planned object IDs, without copying document bodies or making service requests. All entries start unselected. Review the inventory and select the agreed files; provide counts, categories, deferred items and the intended target. If the user already authorized that concrete scope, proceed without another confirmation; otherwise resolve the missing scope before importing.
3. Classify current requirements, features, specs, decisions and reusable lessons as source objects. Existing summaries require explicit dependency mapping; do not import them as independent authoritative facts. Local plan/todo, execution traces and transient hypotheses stay local. Historical change/intake records are optional provenance, selected for actual value rather than loaded with every current document. Inspect selected content for secrets; path exclusions are not a secret scanner. Credential-bearing context requires separate explicit storage/indexing scope, as described in m-memory.
4. Run `apply` with a private, metadata-only journal. The helper imports selected UTF-8 Markdown sources, preserves exact content and records returned revisions. It stops on changed local input, conflict, unavailable service or an uncertain write; resume the same frozen manifest/journal rather than inventing IDs or overwriting existing objects. Partial import is not a completed migration.
5. Complete the information layer using [relationships, summaries and attachments](references/migration.md#information-layer). The local Agent authors or preserves useful summaries and manually reconciles their dependencies. Use source objects as evidence; do not summarize away the only original. Preserve original paths in metadata and create typed references for the selected local links. Explicitly list unresolved/external/excluded links and attachment dispositions. Do not claim they were converted by the text importer.
6. Run `verify` for a fresh full source-content and revision check. Then inspect summaries, dependencies, references and attachments using the appropriate API. Test representative project questions against the old docs and service, including exact parameters, exceptions and an on-demand origin lookup. Search must use the explicitly chosen index/method; do not silently enable embeddings or an external model.
7. Before cutover, stop concurrent edits to the selected source set briefly and recheck the inventory against the current files. If it changed, reconcile that delta with explicit CAS updates and revalidate; the initial importer intentionally does not overwrite an existing service document. Do not call a stale report a clean cutover.
8. When the validated scope is complete and the user authorized switching authority, update the project's AGENTS binding once. All participating worktrees/devices must use that same authority with their own scoped credentials; do not leave two active writers to docs and memory. Retire the migrated local knowledge files only within an explicitly authorized removal scope after verification. The helper never deletes them, changes AGENTS, modifies Git history or chooses backups. Until removal is completed, report the remaining original files; do not present them as a supported offline fallback.

## Finish

Report source root, target library, selected/imported/verified counts, deferred or conflicted files, summary/reference/attachment status and whether cutover happened. Link the private manifest/journal/report when appropriate; never echo credentials or copy migrated bodies into the report. Explain any existing Git-history exposure separately: deleting current files does not erase old commits.

Completion means the selected migration scope and cutover obligations are satisfied, not merely that the helper exited zero. Normal post-migration edits use m-memory and m-* write boundaries rather than rerunning a bulk import.
